## How PVE cloud-init works

When a VM is started, Proxmox VE generates a cloud-init ISO and attaches it
as a virtual CD-ROM drive.  The ISO contains up to four data sources:

| Data source | Generated by | Purpose |
|---|---|---|
| `meta-data` | PVE | VM instance ID and hostname |
| `user-data` | PVE (from VM settings) | User, SSH keys, password |
| `network-data` | PVE (from ipconfig) | IP address, gateway, DNS |
| `vendor-data` | *(not generated by PVE)* | Operator-supplied extras |

Cloud-init reads all four sources on first boot.  `vendor-data` is processed
after `user-data`, making it the preferred place to install extra packages or
run commands without replacing PVE's automatically configured settings.

The `cicustom` VM option lets you replace any of PVE's generated data sources
with a custom snippet file stored on a PVE snippets-enabled storage.

## Hostname

**Hostname always comes from PVE** — do not set it in cloud-init snippets.

PVE writes the VM name into `meta-data` as `local-hostname`.  Cloud-init reads
this on first boot and configures the system hostname regardless of which
user-data mode is used.

```bash
# Set the hostname by naming the VM in PVE (do this before first boot):
qm set <vmid> --name my-server
```

The hostname is also visible and editable in the PVE web UI under the VM's
**General** tab.

## Timezone

PVE has no native cloud-init timezone option — it must be set via a snippet.

The easiest approach is to add it to the **vendor-data** snippet so it applies
to all VMs without replacing PVE's generated user-data:

```bash
# ci-vendor-qemu-guest-agent.yaml already includes timezone: UTC
qm set <vmid> --cicustom "vendor=local:snippets/ci-vendor-qemu-guest-agent.yaml"
qm cloudinit update <vmid>
qm start <vmid>
```

To use a different timezone, edit the `timezone:` value in the snippet.  Find
valid timezone identifiers with:

```bash
timedatectl list-timezones          # Linux
tzsetup -l                          # FreeBSD
```

All [`samples/`](samples/) user-data and vendor-data files include
`timezone: UTC` — replace `UTC` with the appropriate value before deploying.

## Authentication

### SSH public key

The recommended approach.  Configure via the PVE web UI (Cloud-Init tab) or
CLI — no snippet required:

```bash
# Import your public key into PVE (one-time setup)
qm set <vmid> --sshkeys ~/.ssh/id_ed25519.pub

# Or add multiple keys from a file with one key per line
qm set <vmid> --sshkeys /path/to/authorized_keys
```

PVE injects the key(s) into the default user configured for the template
(typically `debian`, `ubuntu`, `rocky`, `opensuse` depending on the distro).

To add a custom user with an SSH key via a snippet, use
[`ci-user-basic.yaml`](samples/ci-user-basic.yaml):

```bash
qm set <vmid> --cicustom "user=local:snippets/ci-user-basic.yaml"
qm cloudinit update <vmid>
qm start <vmid>
```

### Password

Configure via the PVE web UI (Cloud-Init tab → Password) or CLI:

```bash
qm set <vmid> --cipassword 'MySecurePassword'
```

PVE hashes the password and injects it for the default template user.
Password SSH login must also be enabled:

```bash
qm set <vmid> --cipassword 'MySecurePassword'
# ssh_pwauth is enabled by default when a password is set via PVE
```

To set a password for a custom user via a snippet, use
[`ci-user-password.yaml`](samples/ci-user-password.yaml).  Generate a
SHA-512 hash first:

```bash
openssl passwd -6 'MySecurePassword'
```

Then set it in the snippet's `passwd:` field and apply:

```bash
qm set <vmid> --cicustom "user=local:snippets/ci-user-password.yaml"
qm cloudinit update <vmid>
qm start <vmid>
```

### SSH key and password combined

Use PVE native settings to configure both at once (no snippet needed):

```bash
qm set <vmid> \
    --sshkeys ~/.ssh/id_ed25519.pub \
    --cipassword 'MySecurePassword'
qm cloudinit update <vmid>
qm start <vmid>
```

To do this with a custom user via a snippet, include both `ssh_authorized_keys`
and a hashed `passwd` in the user definition — see
[`ci-user-basic.yaml`](samples/ci-user-basic.yaml) as a starting point.

## Network configuration

### DHCP

The simplest setup.  No snippet required:

```bash
qm set <vmid> --ipconfig0 ip=dhcp
qm cloudinit update <vmid>
qm start <vmid>
```

For IPv6 DHCP alongside IPv4:

```bash
qm set <vmid> --ipconfig0 ip=dhcp,ip6=dhcp
```

### Static IP

Configure directly via PVE — no snippet required for common cases:

```bash
qm set <vmid> \
    --ipconfig0 ip=192.168.1.50/24,gw=192.168.1.1 \
    --nameserver "192.168.1.1 8.8.8.8" \
    --searchdomain example.com
qm cloudinit update <vmid>
qm start <vmid>
```

For advanced network configuration that PVE's `ipconfig` does not support
(multiple search domains, custom routes, bonding, VLANs), use a
network-data snippet:

```bash
qm set <vmid> --cicustom "network=local:snippets/ci-network-static.yaml"
qm cloudinit update <vmid>
qm start <vmid>
```

See [`samples/ci-network-static.yaml`](samples/ci-network-static.yaml) for
the network-data v2 format.

## Adding packages and run commands

The safest way to install extra packages without replacing PVE's generated
user-data is a **vendor-data** snippet.  PVE does not generate vendor-data, so
it stacks on top of PVE's config — hostname, SSH keys, and IP config set via
the PVE UI all remain effective:

```bash
qm set <vmid> --cicustom "vendor=local:snippets/ci-vendor-qemu-guest-agent.yaml"
qm cloudinit update <vmid>
qm start <vmid>
```

For a complete user-data snippet with multiple packages and run commands, see
[`samples/ci-user-packages.yaml`](samples/ci-user-packages.yaml).

## Custom snippets via cicustom

`cicustom` accepts one or more `key=storage:snippets/file.yaml` pairs,
comma-separated:

```bash
qm set <vmid> --cicustom \
    "user=local:snippets/ci-user-basic.yaml,vendor=local:snippets/ci-vendor-qemu-guest-agent.yaml"
```

Run `qm cloudinit update <vmid>` after any `cicustom` change so PVE
regenerates the cloud-init ISO before the next boot.

### vendor-data — extend without replacing

`vendor-data` stacks on top of PVE's auto-generated user-data.  Hostname, SSH
keys, and IP config set in the PVE UI continue to work.  This is the
**recommended approach** for adding packages or run commands.

```bash
qm set <vmid> --cicustom "vendor=local:snippets/ci-vendor-qemu-guest-agent.yaml"
```

See [`samples/ci-vendor-qemu-guest-agent.yaml`](samples/ci-vendor-qemu-guest-agent.yaml).
This snippet is required on the PVE host for `pve-import-cloud-images` API mode.

### user-data — full replacement

Setting `user=` **replaces** PVE's generated user-data entirely.  The snippet
must include all required configuration (users, SSH keys, packages).

> **Note:** After setting `cicustom user=`, the **User**, **Password**, and
> **SSH Keys** fields in the PVE Cloud-Init UI tab are ignored.  Only
> **Hostname** (via meta-data) and **Network** (via network-data or ipconfig)
> remain effective.

```bash
qm set <vmid> --cicustom "user=local:snippets/ci-user-basic.yaml"
qm cloudinit update <vmid>
qm start <vmid>
```

### network-data — advanced networking

Setting `network=` replaces PVE's generated network config.  Use only when
`ipconfig` + `--nameserver` + `--searchdomain` are insufficient.

```bash
qm set <vmid> --cicustom "network=local:snippets/ci-network-static.yaml"
```

## FreeBSD (nuageinit)

FreeBSD uses `nuageinit` instead of Python cloud-init.  Key differences from
Linux:

- `nuageinit` **does not read vendor-data**.  Use `cicustom user=` instead.
- `cicustom user=` replaces PVE's generated user-data, so the snippet must
  include all settings (users, SSH keys).
- **Hostname** is still set by PVE via meta-data — do not include it in the
  snippet.
- `qemu-guest-agent` cannot be pre-installed offline (Linux cannot write to
  UFS2 filesystems), so install it via `runcmd` on first boot.

```bash
qm set <vmid> --name my-freebsd-vm
qm set <vmid> --cicustom "user=local:snippets/ci-user-freebsd.yaml"
qm set <vmid> --ipconfig0 ip=dhcp   # or static via ipconfig
qm cloudinit update <vmid>
qm start <vmid>
```

See [`samples/ci-user-freebsd.yaml`](samples/ci-user-freebsd.yaml) for a
complete example.

## Snippet storage setup

Snippets must be stored on a PVE storage with the **snippets** content type
enabled.

**Enable snippets on an existing storage** (PVE web UI):

1. Datacenter → Storage → select the storage → Edit
2. Under **Content**, add **Snippets** → OK

**Enable via CLI:**

```bash
pvesm set local --content vztmpl,iso,snippets,images,rootdir
```

**Place a snippet file on the PVE host:**

```bash
# Default local storage
cp ci-vendor-qemu-guest-agent.yaml /var/lib/vz/snippets/

# Custom storage (adjust path for your mount point)
cp ci-vendor-qemu-guest-agent.yaml /mnt/pve/YOUR-STORAGE/snippets/
```

**Verify PVE can see the snippet:**

```bash
pvesm list local --content snippets
```
